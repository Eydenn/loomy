# AI_MODEL_ROUTING.md

## Principle
The **lead agent** (the main session) has the best reasoning: it plans, splits, delegates, decides, integrates and verifies.
The work itself goes to **dedicated roles**, each on the cheapest model and effort that do it reliably.

This file is the single source of truth for model and effort choices in this repository.
It is generated by Loomy's routing engine: regenerate it rather than editing the matrix by hand.

```bash
.loomy/scripts/ai-route.sh              # the project's coloured matrix
.loomy/scripts/ai-route.sh markdown     # the matrix below
.loomy/scripts/ai-route.sh get executor # a single role, for scripts
```

## Roles
| Role | Scope | Modifies files |
|---|---|---|
| lead | plan, splitting, delegation, decisions, integration, final verification | yes |
| architect | architecture, specs, ADRs, trade-offs | no |
| debugger | hard bugs, long terminal tasks, migrations | no (proposes the fix) |
| security | focused security review (auth, payments, data, secrets) | no |
| reviewer | diff review: regressions, edge cases, missing tests | no |
| developer | everyday features and fixes within an agreed scope | yes |
| executor | precise, bounded tickets, tests, mechanical bulk changes | yes |
| explorer | code search, mapping, summaries, logs | no |
| documenter | README, docs, changelogs | yes (docs only) |

## Lead agent rules
1. Decide before delegating: each delegated task has a scope, acceptance criteria and the list of files involved.
2. Delegate execution; don't spend the best model's tokens on bulk edits, searches or mechanical changes.
3. Check each delegated result against the repository and run the checks yourself before accepting it.
4. Never run two writing roles on the same files at the same time in one working tree.
5. Move up one notch (executor → developer → lead agent, or effort +1) after two failed checks, a result contradicted by the repository, or a scope that turns out to be cross-cutting. Never loop on a cheap model.
6. All HIGH-risk work (authentication, permissions, payments, personal data, migrations, production infrastructure, cryptography, destructive operations) goes through the security role before integration.

## Environments and fallbacks
The environment is derived from the brief (`ai_mode`, `ai_lead`) and the CLIs actually installed:

- **Full Claude Code**: every role runs on Claude models, as subagents in `.claude/agents/`.
- **Full Codex**: every role runs on GPT-6 models, through `delegate-to-codex.sh <role>`, which runs `codex exec` on the routed model.
- **Hybrid, Claude lead**: the lead agent runs on Opus 5.5. Execution goes to GPT-6-Luna through `delegate-to-codex.sh executor`, and cross review through `delegate-to-codex.sh reviewer`.
- **Hybrid, Codex lead**: the lead agent runs on GPT-6-Astra. Architecture, security and hard debugging go to Opus 5.5 through `delegate-to-claude.sh` (read-only), and review to Sonnet 5.

If the mode asks for both tools but only one is installed, routing switches automatically to that tool's full matrix.

In hybrid:
- review always comes from the other model family;
- architect, security and debugger always run on Claude;
- the executor always runs on Codex;
- explorer, developer and documenter stay on the main tool, avoiding a bridge cost.

## Budget profile
The lead agent always stays on the best model. The profile only changes the roles' efforts and models:

- `econome` (frugal): specialists and lead agent at `medium`, execution roles on the fast models;
- `equilibre` (balanced, default): the matrix below;
- `qualite` (quality): lead agent and specialists at `xhigh`, reviews on the best model, executor on the mid model.
